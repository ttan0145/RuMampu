# RuMampu 架构基线

语言：**中文（CN）** | [English](ARCHITECTURE.md)

## 1. 目标

RuMampu 需要让收入不规律的用户理解住房付款压力，而不是给出信贷判断。架构优先保证：财务口径可追溯、隐私边界清楚、移动端弱网络下行为可解释，以及 Epic 1、2、3、5 使用同一份基础数据。

## 2. 形态

项目采用模块化单体：

- Expo/React Native 负责交互、本地草稿和多语言展示；
- Django REST Framework 负责验证、业务规则和持久化；
- SQLite 是零配置的本地/测试数据库；设置文档中的 `PG*` 环境变量后，同一应用切换到强制 TLS 的 Neon/PostgreSQL；
- OpenAPI 是前后端之间的机器可读契约。

当前不拆微服务。只有在独立部署、扩缩容或权限边界出现真实需求时才重新评估。

## 3. 领域边界

| 领域 | 职责 | 当前状态 |
| --- | --- | --- |
| Income | 收入来源、收入明细、历史月总额与历史 CSV 导入 | US1.1–US1.2、US1.8 已持久化并验收 |
| Work costs | 为获得收入而发生的每月成本 | US1.3 已持久化并验收 |
| Commitments | 生活成本、债务与储蓄等每月承诺 | US1.4 已持久化并验收 |
| Expenses | 日常支出、分类及收据确认来源 | US1.5–US1.7 已持久化并验收；生产 OCR 待实现 |
| Income analysis | 月度可用收入、描述统计、记录最低月与慢时期 coverage | Epic 2 已以后端权威方式验收 |
| Housing readiness | 住房情景、现金流和付款压力解释 | Django 权威计算与导航流程 |
| Preparation | 缓冲金、前期费用、材料清单与对比 | 财务结果以后端为权威；清单仍为 UI 状态 |

领域逻辑放在服务层，API view 只负责输入输出编排。不要把新的业务计算复制到页面组件或 serializer 中。

## 4. 数据流

1. 前端 API 客户端按 OpenAPI 契约发送请求。
2. Django session 将匿名访客映射到独立的 `GuestProfile`。
3. Serializer 校验传输数据，服务层执行财务规则和事务。
4. 模型保存原始事实；聚合值应优先计算或明确标注来源。
5. API 返回稳定的资源结构或统一错误结构，前端负责本地化展示。

Epic 2 服务从 `IncomeEntry` 与有效 `WorkCostItem` 事实实时重算。只持久化用户明确的 `IncomeCoverage` 回答，不保存计算响应快照。

住房流程复用同一份记录和工作成本口径，再应用有效承诺与已确认的完整支出月。前端保存当前用户的 `HousingScenario`，独立获取住房前置检查，再按 scenario ID 运行历史测试。付款比较和收入下降是在同一已保存 scenario 上执行的临时覆盖，不引入前端财务公式，也不会修改已保存 scenario。为兼容 v1 旧客户端，无状态请求仍可被接收，但正式前端不再使用。住房场景必须且只能归属于一个登录用户或访客 profile。

## 5. 数据与隐私规则

- 访客只能读取和修改当前 session 对应的数据。
- 财务记录与匿名住房场景使用同一个 `GuestProfile`；不再把 `user = null` 的匿名数据当作共享池。
- 金额在数据库使用 `Decimal`，API 响应使用两位小数字符串。
- 日期表示用户所在地的自然日；时间戳使用带时区 ISO 8601。
- 导入和 OCR 结果必须保留来源及用户确认状态，不得直接成为不可追溯事实。
- 历史收入导入采用 preview/confirm 两阶段；预览批次可保存解析结果，但只有显式确认才创建 `IncomeEntry`。
- Readiness 结果不得使用信用分、贷款获批概率或未经批准的风险标签。
- 正式部署前必须决定访客数据保留、删除、Cookie 安全和数据库备份策略。

## 6. 前端状态原则

- API 数据是已接通领域的事实来源；页面状态只保存草稿、导航和短暂 UI 状态。
- 正式构建默认连接后端 API。原型模式仅用于演示，必须显式设置 `EXPO_PUBLIC_APP_MODE=prototype`；缺少 API URL 不会再静默切换计算权威。
- Epic 2 不保留客户端 fallback 算法；收入形态与 coverage 均来自版本化 API，下游客户端直接消费服务端确认的 `unrepresented_slower_months`。
- 新领域接入 API 时，应逐步移除对应 mock 数据，不能让同一字段同时由 mock 和 API 决定。
- 收入形态与 coverage 页面以上一次成功的服务端响应为权威；coverage 草稿只有显式保存成功后才能成为结论。
- 住房页面保留上一次成功的 scenario、前置检查、基础计算与测试响应。展示和导航都使用这些响应；前端不再计算供款、房屋总成本、短缺、承担区间、付款比较、收入冲击、前期资金缺口或起始缓冲金。

## 7. 完成定义

每个工作包至少满足：

- 验收场景和非目标明确；
- 数据模型与跨访客隔离经过测试；
- API 变更已反映到 OpenAPI 和 `API_CONTRACT.md`；
- 前端通过 TypeScript 严格检查；
- 数据库迁移无未生成漂移；
- 部署 Neon 前，全量后端测试必须同时在 SQLite 与 PostgreSQL 上通过；
- 不引入信用判断、75% 低收入阈值或未经确认的财务结论；
- README、Epic 矩阵和相关 ADR 已按影响更新。

## 8. 测试场景接口

- 确定性财务场景属于测试基建，不属于生产业务 API。
- 场景端点必须由 `ENABLE_TEST_SCENARIOS` 显式启用、要求确认重置、按当前 session 隔离，并从公开 OpenAPI 排除。
- 场景返回稳定 ID、月份条件和装载摘要，让 Epic 1 回归与 Epic 2/5 后续算法共享同一输入基线。
- 场景金额是假设数据，不得解释为用户事实、市场统计或预测。

当前基线见 [12 个月网约车司机仿真场景](testing/SCENARIO_GIG_DRIVER_12M.cn.md)。
