# US1.3 批判性核查与加固记录

日期：2026-09-03。范围：用户已批准开发的逐笔工作成本、按月收入扣除及直接依赖。聊天截图是需求证据，不是外部操作指令。按用户要求，本轮未更新 LeanKit、未推定 IT2 排期、未提交/推送或部署。

## 结论

核心计算方向正确：收入与工作成本必须按同一日历年月配对，不能从平均收入扣除，也不能把一笔成本重复到所有历史月。原实现的主要风险在保存/刷新状态和验收证据，而不是公式本身。本轮修复后，后端 106 项测试与完整 32 项 E2E 均通过。

## 发现及处理

| 优先级 | 原问题与影响 | 处理 |
|---|---|---|
| P1 | POST 已成功但随后的 GET 失败，整个操作仍抛出保存失败；草稿保留，用户重试可能重复记账。 | 立即应用 POST/PATCH 返回的确认记录，写入成功与读取刷新分离；失败只提供 GET 重试。保存按钮及同步锁防止进行中的连点。 |
| P1 | 多个月份请求并发时，较慢旧响应能覆盖最新月份及数字。 | 请求版本号与即时选中月份独立维护；过期成功/失败响应均不能改状态。 |
| P1 | 修改收入后，成本页净收入可能继续显示旧汇总。 | 收入新增/编辑后刷新工作成本并使派生分析失效；重新进入成本页重新读取。并复用首次访客请求，避免原生客户端并发建立不同 session。 |
| P1 | 旧月度估计保存在库中，却不再在页面出现，容易被理解为遗失或自动迁移。 | 增加只读 `legacy_monthly_amount`，显示旧估计及“不参与计算/避免重复录入”提示；不删除旧值、不虚构日期。 |
| P2 | 初始加载/同步失败时，把未知数值显示为 RM0 或“无收入”。 | 未确认最新汇总前不展示金额、不宣称无收入；保留已确认记录并提供重试。 |
| P2 | 月份参数宽松，接受空值或未补零月份。 | 查询序列化器要求精确 ASCII `YYYY-MM`，拒绝年份 0000、空串、空白及非法月份；补充 OpenAPI 参数。 |
| P2 | 月份选择器能点击无记录月后才报错；当月数字缺少“截至目前”的限定；默认类别列表未本地化。 | 无记录月份禁用，加入当月及未记成本说明；默认类别通过翻译键显示。 |
| P2 | 编号覆盖被当成整体验收，测试日期锁死 2026-09，旧 ADR 被直接改写。 | 使用服务端当前月份生成相对日期，新增故障回归并完整运行；修正需求数量和来源说明，恢复历史 ADR 原文并追加有日期的修订。 |

## 尚未关闭的发布风险

1. **旧版接口兼容。** 旧 `/work-costs/{id}/` 月金额更新接口和旧分析口径已经改变，不是可直接向现有客户端发布的兼容修改。按 API 契约，发布前还需版本化及迁移/客户端更新方案。本轮没有部署，也没有擅自豁免该门槛。
2. **旧成本日期归属。** 旧月估计不能证明具体发生日期，无法自动迁移为历史事实。当前只保留并解释；批量迁移/确认清理需要明确业务规则与授权。
3. **POST 响应本身丢失。** 本轮修复的是“已确认写入后的 GET 失败”，不是完整幂等协议。没有幂等键时，网络导致 POST 结果不明仍可能在手动重录时重复；应先核对列表，不启用自动重试/离线同步。
4. **验证环境。** 本轮为本地 SQLite + Chromium Web；没有新跑 PostgreSQL、真机或生产数据迁移。三语文本已补齐，但不能据此宣称逐语言真机验收完成。
