# ADR 0001：模块化单体与版本化 API 基线

语言：**中文（CN）** | [English](0001-foundation-and-api-contract.md)

- 状态：已接受
- 日期：2026-08-24

## 背景

现有 Expo 原型已经覆盖多个 Epic 的页面，但后端仅有第一条收入闭环。若继续按页面逐个实现，收入、成本、承诺、支出和准备模块可能形成不一致的金额、错误、身份与版本规则。

## 决策

1. 采用 Expo 前端加 Django 模块化单体，不提前拆分微服务。
2. 正式业务 API 使用 URL 版本 `/api/v1/`。
3. 使用 drf-spectacular 从代码生成并校验 OpenAPI 3 schema。
4. 成功响应保持资源原形；错误统一使用 `{ "error": { "code", "message", ... } }`。
5. 数据库存储使用 Decimal，API 金额使用两位小数字符串，日期使用 ISO 格式。
6. 当前访客边界使用 Django session；账户体系延后，但领域数据始终关联 profile。
7. 第一版原型路径暂时作为兼容别名存在，但从公开 schema 中排除。

## 结果

- Epic 1、2、5 的后续接口必须遵守同一契约。
- 前端不能根据英文错误文本判断流程，只能使用稳定错误码。
- API 变更需要同时通过测试、schema 校验和文档检查。
- 访客 session 适合当前验证阶段，但生产部署前仍需补数据保留、跨设备迁移、CSRF/Cookie 和账户升级方案。
- 模块化单体降低初期运维成本；若未来出现独立扩缩容需求，再通过新的 ADR 评估拆分。
