# ADR 0005：现金缓冲改按最大跌幅计算

语言：[English](0005-cash-buffer-deepest-fall.md) | **中文（CN）**

- 状态：已采纳，待负责人验收 2026-10-03 的改动
- 日期：2026-10-03

## 背景

`starting_liquidity.required_amount` 是 Cash buffer 页面（US5.3）显示的现金缓冲，也是 Saving plan（Epic 10）的缓冲目标。

原来的算法是：从记录的第一个月开始累计，取运行余额跌到零以下最深的那一点。这样结果取决于记录碰巧从哪个月开始。以 12 个月的共享样例为例：
- 每月成本 RM 1,900 时，从 8 月开始的记录只需 RM 680，同样的月份换成从 1 月开始却需要 RM 1,940。
- 每月成本 RM 1,382.37 时，从 8 月开始算是 RM 0，从 1 月开始则需要 RM 904.74。

AC5.3.2 把缓冲定义为“撑过记录中短缺月份、且不跌破零所需的最小起始金额”。Saving plan 又拿这个数当作买房前要存的钱，所以算少了代价最大。

## 决定

1. `required_amount` 取运行余额从之前某个高点（或从开头）到之后低点的最大跌幅。也就是说：不论从记录里哪个月开始，都能一直撑到记录结束所需的最小起始金额。它永远不低于原来的结果；当最大跌幅从记录开头算起时，两者相等。
2. 跌幅按记录顺序计算，不把记录首尾相接。首尾相接会让一份追不回来的记录把同一段缺口算两次。
3. `starting_liquidity` 新增两个字段：
   - `fall_start`：跌幅起点所在月份，也就是那个高点所在的月份；从记录开头算起时为 null。
   - `fall_end`：跌到最低的月份；余额从未下跌时为 null。

   Cash buffer 页面用它们说明这个数从哪来，并在滚动余额图上标出这段月份。
4. 计算仍在 Django，符合 ADR 0004。

## 影响

- 这改变了一个已有 v1 字段的含义，按 API 契约属于破坏性变更。这次直接原地修改，不开新版本路径，理由有两条：
  - 调用方只有本仓库里的 RuMampu 应用和助手服务，这次已一并更新。
  - 字段含义仍是“需要的起始金额”，数值只会变大。
- 样例回归测试的期望值改为 RM 1,940、RM 904.74、RM 4,740。直接测试逐一计算按时间顺序保留的每段后缀，核对各后缀所需起始现金的最大值等于整份记录的缓冲。不会把月份循环换序；缩短记录可以使缓冲变小，例如从 2026 年 2 月保留到 7 月时为 RM 1,260。
- 已保存的测试（`result_snapshot`）和应用在设备上保留的结果，存的都是当时算出的数字。这次改动之前跑过的测试，在重新运行之前仍显示旧的缓冲。
- 运行余额到记录结束时比开头还低的情况，现在仍把整段跌幅当作一笔缓冲。说明“这些月份追不回来”属于另一条提议中的标准（AC5.3.9），不在本决定范围内。
